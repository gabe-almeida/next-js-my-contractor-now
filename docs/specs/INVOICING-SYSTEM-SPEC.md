# Invoicing System Specification

## Overview

A comprehensive invoicing system for managing **Accounts Receivable** (invoices TO lead buyers) and **Accounts Payable** (payments owed TO affiliates). This system enables super admins to create invoices, track payments, manage Net 30 terms, and maintain complete audit trails.

### Design Decisions Made
1. **Payment terms**: Use `paymentTermsDays: Int` (days as number) for BOTH Buyer and Affiliate extensions. Note: Existing Affiliate has `paymentTerms: String` ("net30") - will coexist, new field takes precedence.
2. **Polymorphic validation**: Application-level enforcement that exactly ONE of `buyerId` OR `affiliateId` is set per invoice.
3. **AffiliatePayment coexistence**: **CONFIRMED** - Keep BOTH systems. `AffiliatePayment` for quick operational payout tracking, `Invoice (PAYABLE)` for formal line-item invoicing. Both records created for affiliate payments.
4. **Invoice number format**: **CONFIRMED** - Use prefixed sequences:
   - `AR-2024-00001` for Accounts Receivable (buyer invoices)
   - `AP-2024-00001` for Accounts Payable (affiliate invoices)
5. **PDF export**: **V1 REQUIRED** - Must have PDF generation from day one.
6. **Overdue handling**: **CRON FROM START** - Implement daily cron job to mark invoices overdue.
7. **Navigation**: Place under new **"Finance" section** in admin sidebar (with Invoices, Payouts grouped).
8. **Lead selection for invoices**: **AUTO-INCLUDE ALL** uninvoiced leads in date range, admin can remove specific ones before sending.

## Race Condition Handling

### 1. Invoice Number Generation

**Problem:** Multiple admins creating invoices simultaneously could get duplicate numbers.

**Solution:** Use database-level atomic increment with `SELECT FOR UPDATE`:

```typescript
// src/lib/services/invoice-number-service.ts
type InvoicePrefix = 'AR' | 'AP';  // AR = Accounts Receivable, AP = Accounts Payable

async function getNextInvoiceNumber(type: InvoiceType): Promise<string> {
  const prefix: InvoicePrefix = type === 'RECEIVABLE' ? 'AR' : 'AP';
  const year = new Date().getFullYear();

  // Use transaction with row-level lock
  const result = await prisma.$transaction(async (tx) => {
    // Lock the row for this prefix + year combination
    const sequence = await tx.$queryRaw`
      SELECT * FROM invoice_sequences
      WHERE prefix = ${prefix} AND year = ${year}
      FOR UPDATE
    `;

    let nextNumber: number;
    if (!sequence || sequence.length === 0) {
      // Create new sequence for this prefix + year
      await tx.invoiceSequence.create({
        data: { prefix, year, lastNumber: 1 }
      });
      nextNumber = 1;
    } else {
      // Increment existing
      await tx.invoiceSequence.update({
        where: { prefix_year: { prefix, year } },
        data: { lastNumber: { increment: 1 } }
      });
      nextNumber = sequence[0].lastNumber + 1;
    }

    // AR-2024-00001 or AP-2024-00001
    return `${prefix}-${year}-${String(nextNumber).padStart(5, '0')}`;
  });

  return result;
}
```

### 2. Payment Recording

**Problem:** Two admins recording payments simultaneously could overpay an invoice.

**Solution:** Use optimistic locking with version field:

```typescript
// src/lib/services/payment-service.ts
async function recordPayment(invoiceId: string, amount: Decimal, data: PaymentData) {
  return prisma.$transaction(async (tx) => {
    // Get current invoice with lock
    const invoice = await tx.invoice.findUnique({
      where: { id: invoiceId },
      select: { id: true, balance: true, status: true, version: true }
    });

    if (!invoice) throw new Error('Invoice not found');
    if (invoice.status === 'CANCELLED') throw new Error('Cannot pay cancelled invoice');
    if (amount > invoice.balance) throw new Error('Payment exceeds balance');

    const newBalance = invoice.balance.minus(amount);
    const newStatus = newBalance.isZero() ? 'PAID' : 'PARTIALLY_PAID';

    // Update with optimistic lock check
    const updated = await tx.invoice.updateMany({
      where: {
        id: invoiceId,
        version: invoice.version  // Optimistic lock
      },
      data: {
        amountPaid: { increment: amount },
        balance: newBalance,
        status: newStatus,
        paidInFullAt: newStatus === 'PAID' ? new Date() : null,
        version: { increment: 1 }
      }
    });

    if (updated.count === 0) {
      throw new Error('Invoice was modified by another user. Please refresh and try again.');
    }

    // Create payment record
    await tx.invoicePayment.create({
      data: {
        invoiceId,
        amount,
        ...data
      }
    });

    return { success: true };
  });
}
```

### 3. Lead Invoicing (Prevent Double-Invoice)

**Problem:** Same lead could be added to multiple invoices.

**Solution:** Check and mark leads atomically:

```typescript
// src/lib/services/invoice-service.ts
async function addLeadsToInvoice(invoiceId: string, leadIds: string[]) {
  return prisma.$transaction(async (tx) => {
    // Check if any leads are already invoiced
    const existingItems = await tx.invoiceLineItem.findMany({
      where: {
        leadId: { in: leadIds },
        invoice: { status: { not: 'CANCELLED' } }  // Allow re-invoicing cancelled
      },
      include: { invoice: { select: { invoiceNumber: true } } }
    });

    if (existingItems.length > 0) {
      const conflicts = existingItems.map(i =>
        `Lead ${i.leadId} already on invoice ${i.invoice.invoiceNumber}`
      );
      throw new Error(`Leads already invoiced: ${conflicts.join(', ')}`);
    }

    // Add all leads atomically
    await tx.invoiceLineItem.createMany({
      data: leadIds.map(leadId => ({
        invoiceId,
        leadId,
        // ... other fields
      }))
    });
  });
}
```

### 4. Status Transitions

**Problem:** Invalid status transitions (e.g., CANCELLED -> PAID).

**Solution:** Validate transitions with state machine:

```typescript
// src/lib/services/invoice-status-service.ts
const VALID_TRANSITIONS: Record<InvoiceStatus, InvoiceStatus[]> = {
  DRAFT: ['SENT', 'CANCELLED'],
  SENT: ['PARTIALLY_PAID', 'PAID', 'OVERDUE', 'CANCELLED', 'DISPUTED'],
  PARTIALLY_PAID: ['PAID', 'OVERDUE', 'DISPUTED'],
  PAID: [],  // Terminal state
  OVERDUE: ['PARTIALLY_PAID', 'PAID', 'CANCELLED', 'DISPUTED'],
  CANCELLED: [],  // Terminal state
  DISPUTED: ['SENT', 'PAID', 'CANCELLED']  // Can resolve dispute
};

async function changeInvoiceStatus(
  invoiceId: string,
  newStatus: InvoiceStatus,
  adminId: string,
  reason?: string
) {
  return prisma.$transaction(async (tx) => {
    const invoice = await tx.invoice.findUnique({
      where: { id: invoiceId }
    });

    if (!invoice) throw new Error('Invoice not found');

    const allowedTransitions = VALID_TRANSITIONS[invoice.status];
    if (!allowedTransitions.includes(newStatus)) {
      throw new Error(
        `Invalid transition: ${invoice.status} -> ${newStatus}`
      );
    }

    // Update status
    await tx.invoice.update({
      where: { id: invoiceId },
      data: {
        status: newStatus,
        // Set relevant dates based on status
        ...(newStatus === 'SENT' && {
          issuedAt: new Date(),
          sentAt: new Date(),
          sentById: adminId,
          dueDate: addDays(new Date(), invoice.paymentTermsDays)
        }),
        ...(newStatus === 'CANCELLED' && {
          cancelledAt: new Date(),
          cancelledById: adminId
        })
      }
    });

    // Record history
    await tx.invoiceStatusHistory.create({
      data: {
        invoiceId,
        oldStatus: invoice.status,
        newStatus,
        reason,
        changedById: adminId,
        changeSource: 'ADMIN'
      }
    });
  });
}
```

### 1. Lead Returned After Invoicing

**Scenario:** Lead is invoiced to buyer, buyer returns lead requesting credit.

**Solution:**
1. Create credit memo (negative invoice line item)
2. Apply to next invoice OR standalone credit invoice
3. Track credit in `InvoiceLineItem` with `itemType: 'CREDIT'`
4. Link credit to original `leadId` for audit trail

```typescript
// Add credit memo
await prisma.invoiceLineItem.create({

    quantity: 1,
    unitPrice: -originalAmount,  // Negative
    amount: -originalAmount,
    itemType: 'CREDIT',
    metadata: {
      originalInvoiceId,
      returnReason: reason,
      returnedAt: new Date()
    }
  }
```

### 2. Buyer Scrub Reconciliation (e.g., Modernize)

**Scenario:** Networks like Modernize scrub ~10% of leads AFTER invoice is sent/paid. They report scrubbed lead IDs at reconciliation time.

**Workflow:**
1. We invoice buyer for ALL delivered leads (100 leads @ $50 = $5,000)
2. Buyer pays full amount ($5,000)
3. Buyer later reports 10 leads as "scrubbed" (invalid, duplicate, etc.)
4. We create credit memo for scrubbed leads on NEXT invoice

**Solution:**
1. Admin uploads/enters list of scrubbed lead IDs from buyer
2. For each scrubbed lead:
   - Update `Lead.disposition` = `'CREDITED'`
   - Create `InvoiceLineItem` with `itemType: 'SCRUB_CREDIT'` on next invoice
3. Credit appears as negative line item on next month's invoice
4. Track actual vs expected scrub rate per buyer for alerts

```typescript
// src/lib/services/scrub-reconciliation-service.ts
async function processBuyerScrubs(
  buyerId: string,
  scrubbedLeadIds: string[],
  adminId: string,
  reason: string
) {
  return prisma.$transaction(async (tx) => {
    // Get leads with their original invoice line items
    const leads = await tx.lead.findMany({
      where: { id: { in: scrubbedLeadIds }, winningBuyerId: buyerId },
      include: { invoiceLineItems: { include: { invoice: true } } }
    });

    // Update lead dispositions to CREDITED
    await tx.lead.updateMany({
      where: { id: { in: scrubbedLeadIds } },
      data: { disposition: 'CREDITED' }
    });

    // Record in lead status history
    for (const lead of leads) {
      await tx.leadStatusHistory.create({
        data: {
          leadId: lead.id,
          adminUserId: adminId,
          oldDisposition: lead.disposition,
          newDisposition: 'CREDITED',
          reason: `Buyer scrub: ${reason}`,
          changeSource: 'ADMIN'
        }
      });
    }

    // Create credit line items for next invoice (or pending credits table)
    // These will be added to the next invoice during creation
    return {
      scrubbed: leads.length,
      totalCredit: leads.reduce((sum, l) => sum + (l.winningBid || 0), 0)
    };
  });
}

// Check scrub rate vs expected
async function checkScrubRate(buyerId: string, periodStart: Date, periodEnd: Date) {
  const buyer = await prisma.buyer.findUnique({ where: { id: buyerId } });
  const leads = await prisma.lead.findMany({
    where: {
      winningBuyerId: buyerId,
      createdAt: { gte: periodStart, lte: periodEnd }
    }
  });

  const totalLeads = leads.length;
  const scrubbedLeads = leads.filter(l => l.disposition === 'CREDITED').length;
  const actualRate = scrubbedLeads / totalLeads;
  const expectedRate = buyer?.expectedScrubRate?.toNumber() || 0;

  return {
    totalLeads,
    scrubbedLeads,
    actualRate,
    expectedRate,
    exceedsExpected: actualRate > expectedRate,
    difference: actualRate - expectedRate
  };
}
```

**UI Flow:**
1. Buyer detail page shows "Reconcile Scrubs" button
2. Admin uploads CSV or enters lead IDs
3. System validates leads belong to buyer and were invoiced
4. Preview shows credit amount and affected invoices
5. On confirm: update leads, queue credits for next invoice
6. Dashboard shows if actual scrub rate exceeds expected

### 3. Affiliate-Generated Lead Sold to Buyer

**Scenario:** Affiliate generates lead -> sold to buyer -> need to track both:
- Invoice to buyer (we receive money)
- Payable to affiliate (we owe money)

**Solution:**
- One lead can have TWO invoice line items:
  1. RECEIVABLE invoice (to buyer) with full price
  2. PAYABLE invoice (to affiliate) with commission amount
- Track relationship via `leadId` on both line items

```sql
-- Query: Get profit margin for affiliate-generated leads
SELECT
  l.id as lead_id,
  ar.amount as buyer_paid,
  ap.amount as affiliate_owed,
  (ar.amount - ap.amount) as margin
FROM leads l
LEFT JOIN invoice_line_items ar ON ar.lead_id = l.id
  AND ar.invoice.type = 'RECEIVABLE'
LEFT JOIN invoice_line_items ap ON ap.lead_id = l.id
  AND ap.invoice.type = 'PAYABLE'
WHERE l.affiliate_id IS NOT NULL;
```

### 3. Partial Payment

**Scenario:** Buyer pays $5,000 on $8,000 invoice.

**Solution:**
- Record payment with `amount: 5000`
- Update invoice: `amountPaid += 5000`, `balance = 3000`
- Set status to `PARTIALLY_PAID`
- Allow multiple payments until `balance = 0`

### 4. Currency/Rounding

**Scenario:** Line items sum to $99.999 due to per-lead calculation.

**Solution:**
- Store all amounts as `Decimal(10, 2)` in database
- Round at line item level (not totals)
- Use `Decimal.js` for calculations to avoid floating point issues

```typescript
import Decimal from 'decimal.js';

// Calculate total from line items
const subtotal = lineItems.reduce(
  (sum, item) => sum.plus(new Decimal(item.amount)),
  new Decimal(0)
).toDecimalPlaces(2);
```

### 5. Overdue Invoice with Partial Payment

**Scenario:** Invoice is OVERDUE, then receives partial payment.

**Solution:**
- Status: `OVERDUE` -> `PARTIALLY_PAID` (stays past due date)
- Keep `dueDate` unchanged
- UI shows "Partially Paid - X days overdue"

### 6. Net 30 Spanning Month Boundary

**Scenario:** Invoice issued Jan 15, due Feb 14. How to track affiliate payables?

**Solution:**
- Affiliate payables are calculated monthly (all leads in January)
- Affiliate payment due: Net 30 from January 31 = February 28
- Separate from buyer invoice dates entirely

```typescript
// Affiliate payable calculation
function calculateAffiliatePayableDueDate(periodMonth: Date): Date {
  const endOfMonth = endOfMonth(periodMonth);
  return addDays(endOfMonth, 30);  // Net 30 from month-end
}
```

### 7. Disputed Invoice

**Scenario:** Buyer disputes charges on an invoice.

**Solution:**
- Status: `SENT` -> `DISPUTED`
- Pause aging/overdue calculations
- Require resolution: either adjust amount or reject dispute
- On resolution: `DISPUTED` -> `SENT` (continue aging) or create credit
