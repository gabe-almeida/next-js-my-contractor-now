## Overview

Implemented the IVR (Interactive Voice Response) webhook handler for the Pay-Per-Call system. This handler processes DTMF responses from callers after they hear the IVR prompt, determining whether they qualify (homeowner) or not (renter).

---

## Files Created

### 1. `/src/app/api/calls/ivr/route.ts` (~400 lines)

**WHY:** Process caller DTMF responses from IVR prompts to determine qualification.

**WHEN:** Twilio redirects here after caller presses a key during IVR.

**HOW:**
- Parses DTMF digits from Twilio webhook
- Validates call is in IVR state
- Processes response based on qualification rules
- Routes qualified callers to auction
- Rejects unqualified callers with appropriate message

**Key Features:**
- Idempotency tracking per IVR step/attempt/digit combination
- State machine validation (IVR -> BIDDING or IVR -> REJECTED)
- IVR data storage in `call.ivr_responses` JSON
- Retry logic with max 3 attempts for invalid input
- Comprehensive logging for debugging and audit trail

**Response Handling:**
| Key | Response | Action |
|-----|----------|--------|
| 1 | Homeowner | Qualify -> Auction |
| 2 | Renter | Reject -> Hangup |
| 9 | Repeat | Replay prompt |
| Other | Invalid | Retry (max 3x) |

### 2. `/src/app/api/calls/auction/route.ts` (~300 lines)

**WHY:** Run real-time auction after caller qualifies through IVR.

**WHEN:** IVR handler redirects here after caller presses 1 (homeowner).

**HOW:**
- Validates call is in BIDDING state
- Runs auction via `CallAuctionEngine`
- Handles winner selection, no bids, and caller hangup scenarios
- Returns transfer TwiML to connect caller to winning buyer

**Key Features:**
- Uses existing `CallAuctionEngine` (no duplication)
- Records auction start time for analytics
- Handles all auction outcomes:
  - Winner found -> Transfer TwiML with recording
  - No bids -> Rejection message
  - Caller hangup -> Graceful exit
- Updates call record with auction results

## Data Flow

```
Caller presses key during IVR
    |
    v
/api/calls/ivr (this handler)
    |
    +-- Parse digits from Twilio
    |
    +-- Validate call state (must be IVR)
    |
    +-- [Digit 1] Qualified
    |       |
    |       +-- Update status: IVR -> BIDDING
    |       |
    |       +-- Log: call.qualified
    |       |
    |       +-- Return: Redirect to /api/calls/auction
    |
    +-- [Digit 2] Not Qualified
    |       |
    |       +-- Update status: IVR -> REJECTED
    |       |
    |       +-- Log: call.rejected
    |       |
    |       +-- Return: Rejection TwiML (hangup)
    |
    +-- [Digit 9] Repeat
    |       |
    |       +-- Log: ivr.repeat_requested
    |       |
    |       +-- Return: Replay IVR prompt
    |
    +-- [Other] Invalid
            |
            +-- If attempts < 3: Retry with new attempt number
            |
            +-- If attempts >= 3: Update status -> FAILED, hangup
```

## IVR Data Schema

The `call.ivr_responses` JSON field stores:

```typescript
interface IVRData {
  flowId?: string;           // IVR flow ID (for multi-step flows)
  currentStep: number;       // Current step (always 1 for now)
  attempts: Array<{
    step: number;            // Which step
    attemptNumber: number;   // Attempt count (1-3)
    input: string | null;    // What they pressed (or null for timeout)
    timestamp: string;       // ISO timestamp
    result: 'valid' | 'invalid' | 'timeout' | 'hangup';
  }>;
  capturedData: Record<string, string>;  // e.g., { homeowner: 'yes' }
  disclosurePlayed?: boolean;
  qualifiedAt?: string;      // ISO timestamp when qualified
  rejectedAt?: string;       // ISO timestamp when rejected
  rejectionReason?: string;  // Human-readable reason
}
```
